# CLAUDE.md

Guidance for Claude Code when working in this repo.

## Keeping this file fresh

This file is a living document. Update it as the repo evolves — when adding/removing augmentations, changing host permissions, restructuring folders, or shifting conventions. Keep entries **high level**: directory roles, plugin patterns, and where things live. Avoid pinning specific DOM selectors, regexes, or detailed flow steps — those drift fast and belong in code comments or the augmentation's own files.

## What this is

A Manifest V3 Chrome/Firefox extension that augments two sites for Northwestern students:

- **CAESAR** (`caesar.ent.northwestern.edu`) — course registration. Adds seat/notes details, CTEC evaluation links, and enrollment-term navigation.
- **Paper.nu** (`paper.nu`, `www.paper.nu`) — schedule planner. Overlays CTEC summaries and analytics onto schedule cards and the section detail panel.

It also reaches Bluera (`northwestern.bluera.com`, which now 301s to the `my-northwestern*.bluera.com` family) and Northwestern SSO hosts to fetch CTEC reports. Report URLs are still built on the legacy origin so cached index entries — deduped by `blueraUrl` — don't fork; host *checks* go through `isBlueraHost` in `src/shared/nu-hosts.ts`.

## Commands

```bash
npm run build          # Build Chrome + Firefox into dist/<target>/
npm run build:chrome   # Chrome only
npm run build:firefox  # Firefox only
npm run dev            # Watch mode (Chrome)
npm run typecheck      # tsc --noEmit
npm run lint           # eslint src eslint-rules — must be 0 errors
npm run test           # vitest run (jsdom env)
npm run test:watch     # vitest watch mode
```

**Always run `npm run build:chrome` after every change** and confirm it passes. Load `dist/chrome` as an unpacked extension. CI (`.github/workflows/ci.yml`) runs typecheck, lint, test, and both target builds on every push to main and every PR — keep all five green. Pushing a `v*` tag runs `.github/workflows/release.yml`, which builds, attaches zips to a GitHub Release, and submits both builds to the Chrome Web Store and Firefox Add-ons (credentials live in the repo's `CWS_*` / `AMO_*` Actions secrets).

## Required pre-push checks for feature changes

Before pushing a user-facing feature or fix, complete both automated checks and live browser QA on the build you intend to ship.

1. **Run regression checks.** Build the extension, run typecheck and lint, and run the tests that cover the changed behavior and nearby flows.
2. **Test with the patched extension active.** Have a Terra subagent use Computer Use to smoke-test the actual user flow in Chrome on the affected site. Alternatively, drive the Aside browser (Chromium, signed in) with the unpacked build loaded there. Control it yourself through the `aside` MCP `repl` tool (Playwright-style); don't hand the flow to Aside's own agent (`aside exec`), which hides what it did. Reload the unpacked build and confirm the patch is active before testing. For flows that write data, use an authorized, reversible sample and verify the result in the destination UI. Remove any test data and confirm the original state is restored.
3. **Hold the push if verification is incomplete.** Fixtures and passing CI do not replace live QA. Fix failures and rerun the affected checks on the revised build. If a login, extension reload, or test setup blocks live QA, report the blocker and wait for help or an explicit waiver before pushing.

## Top-level layout

- `src/background.ts` — service worker. Used for things content scripts can't do directly (e.g. cross-origin fetches).
- `src/content/index.ts` — entry for both CAESAR and Paper.nu. Registers the lookup message handler and starts the augmentation runner.
- `src/content/framework/` — cross-cutting content-script primitives only: the `Augmentation` interface, `AugmentationRunner` (load + debounced mutation re-runs), the shared `el()` / `ensureStyle()` DOM builders in `dom.ts`, and the `createActionButton` / `bindActionButton` factory + styles in `action-button.ts`. The legacy `TemplateAugmentation` abstract class was deleted in Wave 4 — every plugin needed richer state than it modeled. Domain-specific runtimes (e.g. `createPsCellGridRuntime`) live with their domain module, not here.
- `src/content/augmentations/` — one folder per feature. Registered in `registry.ts`.
- `src/content/ctec-index/` — shared CTEC index module (`storage.ts`, `helpers.ts`, `types.ts`, `constants.ts`). Sits outside `augmentations/` because it isn't a registered plugin; `ctec-links` and `paper-ctec` consume it. See "Shared CTEC index" below.
- `src/content/nu-careers.ts` — snapshot of which CAESAR career (school) catalogues each subject, plus `resolveCareerCandidates(subject, catalogNumber)` for ordering them by likelihood (UGRD-first for sub-400, TGS-first for 400+). Consumed by `peoplesoft/context.ts` (Sharper Search Details by class number), `class-search/caesar-search/flow.ts` (Sharper Search course discovery + Add-to-cart) and `ctec-links/fetcher.ts` (CTEC fanout). Without this, lookups would be locked to UGRD + TGS only — Law/SPS/Kellogg-grad/etc. classes would never resolve.
- `src/content/course-aliases.ts` — table of renumbered courses and renamed departments. The prereq canonicalizer maps old ids forward (`aliasCourseId`); the CTEC lookup maps a current course back to its old ids (`formerCourseIds`, via `ctecLookupCourses` in `ctec-links/helpers.ts`), because CAESAR files evaluations under the number a course had when it was taught.
- `src/content/course-history/` — `chrome.storage.local`-backed snapshot of the user's CAESAR Course History (Academic Records → Course History). Populated opportunistically by an AJAX fetch (`SSR_CRSE_HIST_FL`) on every CAESAR page load when the cache is older than 1hr. Read by the popup's "My courses" panel and by the prereq-filter augmentation (which uses Taken/In Progress/Transferred status to score eligibility).
- `src/content/prereqs/` — runtime prereq parser + cache + eligibility evaluator. Ports `__fixtures__/prereqs-parsed.json`'s schema 1:1 (`types.ts`); `parser/` is a recursive-descent regex parser ported from a reference Python implementation; the golden file is now a regression snapshot of this parser, because its and/or grouping rules for comma lists deliberately diverge from the reference. `cache.ts` parses every `PaperCourse.prereqs` from paper.nu's `plan.json` once per `info.plan` revision, persists to `chrome.storage.local` with a 75-day TTL safety net. `overrides.json` is a hardcoded snapshot of current prereq text for courses where paper.nu's is stale, applied before parsing. `canonicalize.ts` runs over the final map (after prereq-filter's term overlay) and rewrites course references against the live catalog: renumbered-course aliases, retired alternates, old department codes, bare numbers, and misparsed "N 200-level courses" phrases. `eligibility.ts` is a pure evaluator over `PrereqNode + course-history` returning `{state, missing, notes}`. Consumed only by `prereq-filter`. Fixture under `__fixtures__/` is loaded only by `parser.spec.ts` and is asserted out of the production bundle by `scripts/build.mjs`.
- `src/content/peoplesoft/` — typed wrapper around CAESAR's PeopleSoft AJAX (context, http, params, parsers, lookup, traffic mutex). Also home to `ps-cell-grid.ts` — `createPsCellGridRuntime`, the composable runtime that handles page-id gating, header / cell injection, in-flight dedupe, retry, ticker lifecycle, and lossless cleanup for any plugin that grafts extra columns onto a PeopleSoft grid (today seats-notes + ctec-links).
- `src/content/cart-cache/` — shared `chrome.storage.local`-backed snapshot of the user's CAESAR shopping cart and current enrollment, keyed by `STRM` (term). class-search and paper-ctec read it to render persistent "In cart" / "Enrolled" badges on Add-to-cart buttons (instead of a transient "Added!" flash) and write to it optimistically when their flow successfully adds. The `CartPageHydrator` augmentation (registered, no user toggle) parses `#SSR_REGFORM_VW$scroll$0` + `#STDNT_ENRL_SSVW$scroll$0` whenever the user lands on the live cart page and replaces the term's entry — this is the only path that drops sections. `reconcile.ts` runs once per CAESAR content-script load when the cache is older than 1hr: background-fetches `CART_URL`, parses, writes. Aborts silently on login-page response.
- `src/content/settings.ts` — feature-toggle state, backed by `chrome.storage.local`. Defaults are on unless overridden in `DEFAULT_FEATURE_STATES`.
- `src/content/messaging.ts`, `src/content/remote-fetch.ts` — message plumbing and background-mediated fetches. `remote-fetch.ts` sends every CAESAR `/psc/csnu/` request through a separate PeopleSoft window (`csnu_<n>`) and renames the response's `win<n>` tokens back to `win0`. PeopleSoft keeps only a few page states per window, so background requests in the user's own window expire the page they are looking at.
- `src/content/design/` — design system. `tokens.ts` declares every `--bc-*` CSS custom property and the per-theme override blocks: `bright` (the pencil.nu website's look: ink accent, warm paper neutrals, yellow only for the one primary action via `--bc-color-cta*`, pink only as chart ink via `--bc-color-chart*`; the default for anyone with no saved choice), `default` (legacy NU purple) and `pencil` (Ticonderoga cream + eraser pink), both still selectable in the popup. `ui-icons.ts` holds the small drawn control icons (16 grid, round caps) that replace text glyphs and emoji; `icons.ts` holds the season and face pictures. `components.ts` declares every higher-level `.bc-*` class built from those tokens, including pencil-specific accents (`.bc-card--paper`, `.bc-btn--pencil`, `.bc-mark`, `.bc-scribble`, `.bc-stamp`, `.bc-divider--dashed`). `index.ts` runs theme bootstrap and exposes `BC_THEMES` + `THEME_LABELS`. `icons.ts` holds the shared drawn icons (four seasons for terms, four faces for comment tone), colored from tokens and restylable by a parent through `--bc-icon-*` properties. Style modules consume vars/classes — never embed raw color literals. To switch the look-and-feel, edit a token block or add a new `[data-bc-theme="X"]` block. The popup exposes a theme dropdown that writes to `chrome.storage.local`. Paper.nu's `.dark` class is mirrored onto `<html data-bc-mode="dark">` so each theme owns its dark variant. Web fonts ship as woff2 in `src/assets/fonts/`; `tokensCss()` emits `@font-face` blocks via a URL-resolver argument so the same code path works for popup (`chrome.runtime.getURL`) and content scripts. SVG-emitting JS in `paper-ctec/{chart-histogram,hours-density,modal/*,analytics-preview}.ts` now sets fills and strokes via `el.style.{fill,stroke} = "var(--bc-color-*)"` so chart colors flow with the active theme + dark mirror automatically — no per-attribute CSS overrides needed.
- `src/popup/` — popup UI with toggle switches and "clear CTEC cache" / "clear catalog cache" / "clear cart cache" buttons. The "What's new" panel at the top reads from `src/popup/changelog.json` (see "Changelog" below).
- `src/shared/messages.ts` — typed message contracts shared across contexts.
- `src/shared/log.ts` — debug-gated quiet logging (`logQuiet`, `logDebug`). Production is silent unless the user runs `localStorage.setItem("bc-debug", "1")`. Use `logQuiet(scope, err)` instead of empty `} catch {}` blocks; the eslint config bans bare empty catches.
- `src/manifest.base.json` — base manifest; `scripts/build.mjs` patches it per target.

## Action buttons

Every async-action button (one whose click triggers a network request, computation, or multi-step flow) MUST go through `createActionButton` from `src/content/framework/action-button.ts`. The factory enforces:

- Synchronous `disabled` lock on the very first click — set BEFORE the first `await`, so back-to-back synchronous double-clicks cannot double-fire the action.
- Loading-state visual feedback via `dataset.state="loading"` + a configurable `loadingLabel` (defaults to "Loading…").
- Click-once semantics: while state is non-idle, additional clicks are no-ops, except retryable error states which return to idle on the next click.
- AbortSignal plumbed into `onClick`, fires when `destroy()` runs mid-flight.
- Result-driven state machine: `void` → idle, `{ kind: "success", sticky: true }` → terminal locked, `{ kind: "success" }` → flash then idle, `{ kind: "error", retryable }` → re-enabled for retry, thrown error → retryable error.

Pure-DOM buttons (Cancel, Close, Toggle visibility) can stay as `el(doc, "button", ...)` — they don't have async work to gate. Only buttons whose click handler is `async` (or returns a Promise) need the factory. Fire-and-forget storage writes can opt out by wrapping the call in `void` (e.g. `() => void persistDismissal()`); the lint rule treats `void` as the documented escape hatch.

A few raw `<button>` elements stay outside the factory because a dedicated controller owns the full state machine externally (today: `class-search/views/section-row.ts` Add-to-cart + Details). Those buttons must carry `[ACTION_BUTTON_MARKER_ATTR]: "controller"` so the lint rule recognizes them as the formalized controller-managed exception. The factory's own output uses the value `"1"`.

Enforcement lives in the local ESLint plugin under `eslint-rules/` (rule `bc-rules/no-raw-action-button`). It's an AST rule wired into `npm run lint`. It catches `addEventListener("click", async …)`, `.onclick = async …`, `el(doc, "button", { on: { click: async … } })`, the same patterns with bodies that contain `await` or top-level `.then`/`.catch`/`.finally` chains, and raw `setAttribute("data-bc-action-button", …)` stamps in files that don't import the factory. See the rule's header comment for the full pattern catalogue and known limitations. Adding a new button that does network/storage/multi-step work without going through the factory will fail CI.

## Augmentation pattern

Each feature lives in `src/content/augmentations/<name>/` and exports a plugin instance from `index.ts`. Most use `TemplateAugmentation` (`appliesToPage` → `collectTargets` → `fetchData` → `renderSuccess`/`renderError`). Some (e.g. CTEC links, paper-ctec) implement `Augmentation` directly when they need richer state (in-flight tracking, retry-on-demand, multi-tab UI, etc.).

The runner invokes plugins on initial load and after every DOM mutation (debounced via `requestAnimationFrame`) — needed because PeopleSoft and Paper.nu both navigate via in-place DOM swaps. Each plugin is gated by `isFeatureEnabled(id)`.

When the user toggles a feature off, the runner calls the plugin's optional `cleanup(doc)` method (and skips its `run()` thereafter). `cleanup()` must remove every DOM node, class, dataset marker, and injected style the plugin ever added — host pages must look indistinguishable from the never-installed state. Sub-flag flips (e.g. dense-cards on/off) just trigger another `run()` on the still-enabled plugin; in-place toggles via `classList.toggle(class, enabled)` and signature-based re-render handle these without needing cleanup.

To add a new augmentation:

1. Create `src/content/augmentations/<name>/` with `index.ts` exporting a plugin.
2. Register it in `src/content/augmentations/registry.ts`.
3. Add it (and any sub-toggles) to `FEATURE_SECTIONS` in `src/popup/popup.ts`.
4. Implement `cleanup(doc)` to fully undo every DOM mutation `run()` makes.

## Current augmentations

- `seats-notes` — CAESAR shopping cart: loads class notes, attributes, requirements, seat counts.
- `ctec-links` — CAESAR shopping cart: per-class CTEC evaluation history widget. Fetches via Bluera and writes a shared CTEC index.
- `enrollment-navigation` — CAESAR: smoother navigation across enrollment terms / registration screens.
- `caesar-history` — CAESAR: makes the browser's Back and Forward buttons work inside CAESAR. PeopleSoft swaps pages in place over AJAX and never touches browser history, so this plugin adds a history entry whenever the view changes and brings the earlier view back on Back/Forward. One mechanism covers every page: a view is named by the selected left-hand tab, the page title and headings, Pencil's Sharper Search / Classic CAESAR tab and whether a PeopleSoft dialog is open (`page.ts`). All entries live in the top window's history, including views that change inside the content frame CAESAR embeds classic pages in, so the browser never reloads the frame on its own. Going back puts a saved copy of the page's form back, `ICStateNum` included, and the server resumes from it; it keeps only the current state plus five earlier ones per PeopleSoft window, and `stack.ts` models which copies are still resumable. A copy too old (or older than a cart/enrollment change) is loaded afresh instead: by re-opening its left-hand tab, or by reloading. Views in a frame or beside a step-list tab layout are always re-opened, never restored, because the tab list sits outside the form. An open dialog is closed with its own Cancel. The choices (one entry per tab switch, restore vs re-open vs reload) live in `decide.ts`, kept pure for unit tests. A restore calls `AugmentationRunner.reset()` so every other plugin re-attaches to the restored DOM. Registered first so it copies each page before other plugins add to it. Adds nothing visible. Default ON. Live check: `scripts/qa/caesar-history.aside.js` drives a signed-in CAESAR in the Aside browser REPL (read-only: opens tabs, searches, opens details, presses Back/Forward). Load the file in the REPL, then `await qa.run(group)` for each of `qa.GROUPS`, one group per REPL call because a call may run two minutes at most; tiles with many tabs are walked in chunks listed by `qa.tileChunks()` (`qa.run(tile, { from })`). Fixtures and unit tests do not replace it.
- `caesar-go-to` — CAESAR: right-aligned bookmarks in both native header layouts and a persistent header on standalone PeopleSoft pages. Adds a CAESAR home wordmark when native branding is absent, preserves native navigation controls, provides an Enrollment Dates preview, and scopes styling to the cart and dates page. The Class Search, Cart and Enrollment Dates links open as tabs of CAESAR's Manage Classes page and Course History opens in Academic Records, so the top bar and left-hand tab list stay; Manage Classes cannot be linked to a tab, so the link names the tab in its fragment and the plugin picks it after load.
- `class-search` — CAESAR: augments both the standalone and Shopping Cart search forms with a paper.nu-powered search UI behind a Better/Classic tab toggle (state in `sessionStorage`). Single search box matches paper.nu-style (whitespace-tokenized, `x` digit-wildcard, ranks subject+catalog hits above title hits). Distro / discipline pills filter further. Per-course **Load CAESAR data** button runs CAESAR's catalog search and paints class number + status badges on each section row. Per-section **Details** expands an inline panel with seats, capacity, class attributes, enrollment requirements, and class notes — driven by `lookupClass(classNumber)` and rendered via the same `seats-notes/parser.ts` pipeline (with shared `seats-notes` cache so a section opened here is already warm if the user later visits their cart). Per-section **Add to cart** drives the full Search → Select → Next chain in the background (`caesar-search.ts → addSectionToCart`); the user never leaves the page. Per-section **CTEC chip + Analytics** (under `ctec/`) reuses paper-ctec's analytics modal and chip helpers (`widget-chips.ts`, `ModalController`); coordinator (`ctec/coordinator.ts`) holds its own resolved/inFlight maps so cross-augmentation fetches don't short-circuit each other, while the underlying subject-index cache (read by `ctec-links/reports.ts → fetchCtecReportAggregate`) IS shared so a fetch in either surface warms both. Mount injects paper-ctec's stylesheet (`injectStyles`) for the chip + modal visuals; cleanup removes both `bc-paper-ctec-style` and `bc-paper-ctec-analytics-modal`. Display formatting strips paper.nu's "-0" suffix (`COMP_SCI 333`); the underlying CAESAR catalog field gets the bare number (`333`) with `contains` match, then we disambiguate by parsing the result group title (`COMP_SCI 333-0` vs `333-SG`). Catalog data cached in `chrome.storage.local` keyed off paper.nu's per-source `updated` timestamps (`paper-data.ts`). Requires `unlimitedStorage` since `plan.json` + per-term files exceed the default quota.
- `course-history-view` — CAESAR Course History: groups the native grid by term (newest first, with per-term class/unit counts, classes indented under each term) and shows inline Status and Subject filter chips in the grid header in place of CAESAR's status-only Filter button. In Cart is off by default; the subject row shows the biggest subjects and expands to the rest. Downloads the visible rows as CSV. Moves and hides CAESAR's own rows instead of cloning them, so each row's native click still opens the Class Information popup and CAESAR's column sort applies within each term. Filter choices persist in `sessionStorage`. Default ON.
- `paper-ctec` — Paper.nu: overlays CTEC summaries on schedule cards and analytics in the section side panel. Has its own sub-toggles (single summary card, dense cards, dense card stars). Analytics render as a sheet (`modal/view.ts` + `summary.ts`, `comments.ts`, `dry-run.ts`; styles in `styles/sheet.ts`). On Paper.nu the sheet lives inside Paper.nu's own Section Info panel, with a Paper.nu / CTECs tab pair that `side-card-coordinator.ts` adds to the panel's header row; the CTECs tab widens the panel, and a card's Analytics button opens the panel on that tab. Where there is no such panel (CAESAR, or Paper.nu failing to open one) the sheet docks to the right edge instead: one scrolling column whose header term switch turns the whole sheet into one term's CTEC. `modal-controller.ts` and `modal/data-controller.ts` own state and fetching; the same sheet opens from CAESAR's Sharper Search. That table is generated by `scripts/fit-sentiment-model.mjs` from labeled comments, which are private and kept out of the repo; refit instead of editing it by hand.
- `prereq-filter` — Paper.nu: eligibility badges + tri-state filter chip on the schedule Search panel, minimal ✓/? badge on schedule-grid cards. Driven by `src/content/prereqs/` (parser + parsed-prereqs cache + pure evaluator) and the `course-history` cache. Default-off feature toggle. Cleanup tears down every badge, chip, tooltip, dataset marker, and injected stylesheet.
- `paper-hide-taken` — Paper.nu: hides search-result cards for courses the user has already completed. Reads the `course-history` cache and drops cards whose `(subject, catalog)` shows up with status `Taken` or `Transferred`. Repeatable courses (`PaperCourse.repeatable === true` in plan.json — covers 396/397/399, seminars, independent study) are never filtered. The "Hide Taken" switch mounts into prereq-filter's `SEARCH_ROW_ID` controls row (the two augmentations share that row above the search results list), inserted right after the feature switch so the visible order when searching is `[Hide Taken, Show Only Prereq Fulfilled]`. Visibility is search-state driven: `isUserSearching(doc)` reads the absence of paper.nu's Browse/Filter strip (`.m-4.flex.justify-center.gap-2`) as the "user has typed" signal. The "Prereqs (Beta)" feature toggle is shown only when NOT searching; "Hide Taken" + "Show Only Prereq Fulfilled" only when searching. Default ON. Mount id `paper-hide-taken-mount` is decoupled from the feature flag so flipping the feature off doesn't tear the switch down.
- `paper-combos` — Paper.nu: schedule combinations generator. Reads paper.nu's `data_schedule` from its localforage IndexedDB (same-origin, untouched), groups canvas sections by course, and enumerates every non-overlapping combination (one section of each scheduled component per course, so a lecture travels with its discussion or lab) via backtracking with a hard cap (5000) and `maxClasses` user input. Sorts combos by mean instruction-rating from the cached CTEC aggregate (`getCachedReportAggregate`); missing data imputed at the neutral midpoint so unrated electives don't sink results. UI: a top-of-grid bar (margined down ~3.25rem to clear paper-ctec's floating status bar) with cycle controls (`← X / Total →`), an avg-rating chip, the max-classes input, and per-course pin chips. Does NOT render its own cards — keeps paper.nu's native ScheduleClass cards intact (color, add-to-cart, paper-ctec chips, etc.) and just toggles `data-bc-paper-combos-hidden="1"` on cards whose section_id isn't in the active combo. Card → section_id resolution: derive expected (day column, hour cell, top%) from each `ComboSection.blocks` entry and match the existing card by that triple plus its `{subject} {number}` text prefix; unmatchable cards (custom sections, partial DOM hydration) stay visible — fail-open. No writes to paper.nu state. Default-off feature toggle.
- `paper-brand` — Paper.nu: grafts a small "with pencil" mark + inline pencil SVG into paper.nu's sidebar logo button so the user can see at a glance that the extension is active. Finds the host button by walking up from `img[alt="paper.nu"]` (alt is stable across paper.nu's hashed PNG filenames), appends a decorative `<span>` after the image, and flips the parent button to `flex-direction: row` via a CSS override keyed off `[data-bc-pencil-brand="1"]`. The mark uses `var(--bc-font-hand)` so the pencil theme's Caveat handwriting font carries through; default-theme users fall back to a Caveat/cursive stack so the handwritten look is preserved either way. The pencil glyph is inlined SVG (mirrors `assets/icons/pencil.svg`) — no manifest `web_accessible_resources` entry needed. Clicks on the mark are swallowed with `stopPropagation` so paper.nu's home/refresh handler on the logo button still works from every other surface but the mark itself feels non-interactive. - `paper-enrollment-dates` — Paper.nu: shows general registration windows and assigned CAESAR appointments from the Paper.nu banner for the quarter being planned. Shares the enrollment dates loader, private appointment display, and Google Calendar draft links with the CAESAR bookmarks. Default ON.
- `paper-export-helper` — Paper.nu: intercepts clicks on the "Export to calendar" item inside paper.nu's EXPORT dropdown menu and opens a walkthrough modal with per-app import steps (Google Calendar / Apple Calendar / Outlook), a central-time warning, and "Open <calendar>" deep links. Detection in `detection.ts` finds the button by its inner `<p>Export to calendar</p>` label (paper.nu's icon+label button convention). We intercept this intermediate button rather than the top-level EXPORT so paper.nu's other export options in the dropdown (if any) stay untouched. The button only exists in the DOM while the dropdown is open; the AugmentationRunner's mutation-driven re-ticks pick it up as soon as it mounts. The modal's "Download .ics" CTA walks paper.nu's own flow on the user's behalf: bypass-click "Export to calendar" (the `allowNativeClickThrough` flag lets the capture-phase interceptor pass the event through), poll for the Download button to mount inside paper.nu's modal via `waitForDownloadButton`, click it to trigger the .ics save, then dispatch Escape to dismiss paper.nu's modal — so the user is left with just the downloaded file and our walkthrough on top. Last-selected tab persists to `chrome.storage.local` (pre-warmed on construction so the click handler can open the modal synchronously). Default ON.

Paper.nu cart adds check this tab's term against the saved schedule and require a single matching section. Sharper Search checks the Paper.nu catalog for CAESAR's selected term before replacing the native form and restores the search view when revisited in the same tab.

Sharper Search matches section titles and topics as well as course names and numbers; topic searches narrow the result to matching sections, whose topic names appear above their details. The CAESAR navigation's Pencil button opens the same About dialog as Paper.nu's brand mark (`paper-brand/modal.ts`); the dialog owns its Escape listener.

Paper.nu's Markdown schedule copy runs only after the user clicks its Export menu item. The extension does not request clipboard permissions; copying uses the browser's normal user activation.

## Mobile app (`mobile/`)

An iPhone and Android app (Capacitor + Ionic React) that runs this repo's own modules from `src/` unchanged. It has its own screens (Schedule, which is home and shows planned, in-cart and enrolled classes as one week; Search; Walk; course page; section sheet; You), drawn with the extension's design system and hosting its CTEC analytics sheet, instead of grafting onto CAESAR or Paper.nu, and the same principles: open source, no servers, everything on the phone.

- `mobile/src/platform/` is the seam. `chrome-shim.ts` stands in for the extension APIs: `chrome.storage.local` is IndexedDB, and `chrome.runtime.sendMessage` fetches go to the native `NUSession` plugin. It must be imported before any `src/` module. `sign-in.ts` shows Northwestern's own sign-in pages and retries; `session-state.ts` tracks signed-in and off-campus state from responses.
- `mobile/src/data/` wraps extension code for the screens (catalog, CAESAR live seats / details / cart / history / add to cart, CTECs, the on-phone schedule). Add features here by calling existing `src/` functions, not by copying them.
- Schedule also hosts combinations (`data/combos.ts`, on the `paper-combos` enumerator and sort modes; enrolled classes are fixed, cart and planned ones are the choices) and registration dates (`data/registration.ts`, on `enrollment-dates`). In a wide window there is no separate Search screen: the search (`useSearch` in `SearchPage.tsx`) runs down the left of Schedule, a picked course (`CourseView` in `CoursePage.tsx`) opens as a second panel beside it, and the schedule (week, then its lists) keeps the rest. A Walk tab (`WalkPage.tsx`) draws a day's walk between classes (`components/Trail.tsx`) from a building table (`data/buildings.ts`); the map is drawn in the app from shapes bundled in `data/campus-map.ts` (generated by `mobile/scripts/campus-map.py` from OpenStreetMap, credited on screen), with no map tiles fetched.
- The native plugin (`ios/App/App/SceneDelegate.swift`, `android/.../NUSessionPlugin.java`) holds the session: sign-in in a web view, requests through a native HTTP session with those cookies. Requests claim a desktop browser and screen, and CAESAR's page session is restarted after sign-in, because CAESAR serves phones a layout the parsers don't know. iOS keeps the session in the Keychain.
- Sync keeps planned classes the same on a student's own devices. Devices are paired by one secret, carried by a link or QR code (`components/PlanTransfer.tsx`, opened from You). `data/sync-core.ts` derives the relay address, write token and encryption key from it and holds the merge rule (newest change per class wins, removals are remembered); `data/sync.ts` runs it against the relay in `relay/` (a Cloudflare Worker that stores one encrypted blob per address and cannot read it). `VITE_SYNC_URL` points a development build at a local relay (`npx wrangler dev --local` in `relay/`). `data/share.ts` reads one-off plan links, Paper.nu share links included, and receives links the app is opened with (`pencilnu://plan#…`, registered by all three shells; the Mac app and a development iPhone build take `-link <url>` as a launch aid). The relay is deployed as `pencil-sync` on Cloudflare; the app reaches it at `www.pencil.nu/sync` (the bare domain redirects, which a web view's preflight request cannot follow), which the website passes through. `platform/keep-alive.ts` asks CAESAR for a page every ten minutes while signed in so the session does not idle out.
- CAESAR only answers on campus Wi-Fi or the VPN, so every live feature needs an off-campus state; saved data must keep working.
- Changing a `src/` module the app imports can break the app: run `npm run typecheck` in `mobile/` as well.
- `mobile/mac/` is the Mac app: a small AppKit window (`PencilMac.swift`) around the same web bundle, without Capacitor. It serves the bundle from inside the app and answers the `NUSession` calls through one message handler (`platform/native.ts` picks it when present). The session logic itself is `ios/App/App/NUSessionCore.swift`, shared by the iPhone plugin and the Mac app. `mobile/mac/build.sh` compiles it with `swiftc` into `mobile/mac/build/Pencil.app` (a release build also makes the notarized `Pencil.dmg` that pencil.nu links to); its icon is `mac/AppIcon.icns`, made from `mac/icon.svg` by `mac/icon.sh`; launching with `-route <route> -shot <png> -after <seconds>` saves a picture of a screen and quits.
- `mobile/desktop/` is the Windows and Linux app: an Electron shell (`main.js`, `preload.js`) around the same web bundle. It mirrors what the Mac shell and `NUSessionCore.swift` do (serve the bundle, show Northwestern's sign-in window, make the app's requests with that session, kept in a cookie store of its own) and exposes the same message handler, so `platform/native.ts` treats it like the Mac app. `npm start` in that folder runs it against `mobile/dist`; it takes `--route=`, `--link=`, `--shot=` and `--after=` like the Mac app's launch aids. `.github/workflows/desktop-release.yml` builds an unsigned Windows installer on `desktop-v*` tags.
- A one-time welcome (`components/Welcome.tsx`) opens on first launch in every app.
- Windows 900px and wider (the Mac app, tablets) get the wide layout in `theme.css`: a side list instead of tabs, the week beside the class list, sheets as dialogs. `platform/wide.ts` is the matching hook.
- Dev loop: `mobile/deploy.sh` builds and installs on the iOS simulator named in `mobile/.sim-udid`; `mobile/shot.sh <route> <name>` opens a screen by route and saves a screenshot. `PENCIL_CTEC_BYPASS=1` turns the CTEC access check off in a development bundle only. Android builds with Android Studio's bundled Java (`JAVA_HOME`), not the system one.
- Release: `mobile/android/release.sh` builds the signed Play bundle and a direct-install file, using a key kept outside the repo (`PENCIL_ANDROID_KEYSTORE`, see `android/app/build.gradle`). The Mac release is `mac/build.sh release`, run by `.github/workflows/mac-release.yml` on `mac-v*` tags. `mobile/store/listing.md` holds the store text and form answers. The iPhone and Android icons follow `mac/icon.svg`. Release builds must not set `PENCIL_CTEC_BYPASS`.

## Changelog

The popup's "What's new" panel reads from `src/popup/changelog.json`. When you ship a release (i.e. bump `version` in `src/manifest.base.json` and `package.json`), prepend a new entry to the `entries` array. The file's `$exampleSchema` key documents the shape — leave it in place.

**Write for the user, not the commit log.** The audience is a Northwestern student opening the popup, not a developer reading `git log`. Each entry should make it instantly clear what changed and what's now possible.

- **High level only.** Group related commits into one feature-shaped item. Don't list every commit, refactor wave, or internal coordinator rename. If five commits added the schedule combinations bar, that's *one* `feat` line, not five.
- **One sentence is great.** A good item is short and concrete: "Generate every non-overlapping schedule from your planned courses on paper.nu." Not: "Adds new augmentation reading data_schedule from localforage IndexedDB and enumerating combinations via backtracking."
- **No jargon.** Don't mention file paths, type names, render-signature dedupe, mutex queues, or any other internal plumbing. The user does not care that we extracted a coordinator.
- **Skip pure internals.** Refactors, lint-rule additions, dependency bumps, type tightenings, and test-only changes do not belong in the changelog. If the user can't see or feel it, leave it out.
- `kind: "feat"` for things the user can now do; `kind: "fix"` for things that were broken and now aren't.
- Optional `headline` on the latest entry sets the section title; keep it punchy (≤ 6 words).

When in doubt, ask: "Would a student understand and care about this in one read?" If not, rewrite it or drop it.

## Shared CTEC index

`src/content/ctec-index/` is the home of the shared CTEC index module — `storage.ts`, `helpers.ts`, `types.ts`, `constants.ts`. It lives outside `augmentations/` because it isn't a registered plugin; it's a sibling module that augmentations consume. `ctec-links` (and indirectly `paper-ctec` via `ctec-links/reports.ts`) read and write the `chrome.storage.local`-backed index through `readSubjectIndex`/`writeSubjectIndex`. The popup's "Clear CTEC cache" button wipes it.

The CTEC-access check (`access*.ts`) sits behind `CTEC_ACCESS_CHECK_ENABLED` in `access-shared.ts`. Flipping it to `false` bypasses the check for local debugging; a spec fails if it's `false`, so CI and the release workflow won't ship the bypass.

paper.nu schedule cards only carry instructor last names. `paper-ctec/instructor-enrichment.ts` resolves them to full names (user's scheduled sections first, then the whole term, matched on each section's own catalog number so cross-lists resolve) before every CTEC read and fetch — bare last names never match CAESAR rows that carry a first initial. It reads paper.nu's saved schedule through `paper-combos/data.ts`.

## User preferences

- Use a Terra subagent for live browser verification of user-facing changes, including local review builds. Aside (see the pre-push checks above) is an accepted alternative.
- Bump the extension version and update the popup changelog when preparing a build with user-facing changes for review.
- Build after every change — `npm run build:chrome` must pass before considering work done.
- Keep solutions minimal — don't add abstractions, error handling, or features beyond what's asked.
- No time estimates.
- Update this file when the structure or feature set changes meaningfully.
